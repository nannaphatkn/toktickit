# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
The goal of this sprint is to deliver a professional, responsive, and functional Requester (end-user) ticketing experience for TokTickIT. This includes ticket creation with attachments, viewing owned tickets, searching/filtering/pagination, and a temporary Development Requester selection mechanism for simulated identity.

## 2. Stakeholder Request Interpretation
The IT department needs a system to receive and manage support tickets. Requesters must be able to log in (simulated for now), create tickets by selecting categories, systems, priority, and attaching files. They also need to view their tickets in a paginated list with search and filter capabilities, and view individual ticket details. Requesters must only see their own tickets.

## 3. Scope
### Included
- Development Requester selection screen (testing mechanism).
- Create Ticket workflow with attachment uploads.
- My Tickets paginated list view with search, filter, and sorting.
- Requester Ticket Detail screen (view mode) with attachment soft removal.
- Ownership protection (preventing cross-requester access).
- Responsive Zen Green Theme UI components.

### Excluded
- Real authentication (login, passwords, sessions, roles).
- IT Staff workflow (staff dashboards, claiming, reassignment).
- Ticket collaboration (Public Comments, Internal Notes).
- Ticket lifecycle progression beyond initial creation (resolution, closing).
- Administration functions.

## 4. Functional Requirements
- **FR-01 (Requester Selection):** The system shall allow users to select an active Development Requester to simulate login.
- **FR-02 (Requester Context):** The application shall display the selected Requester's name and allow switching to a different Requester.
- **FR-03 (Ticket Creation):** A selected Requester shall be able to submit a new ticket by providing a summary, description, category, related system, and requested priority.
- **FR-04 (Attachment Upload):** A Requester shall be able to upload up to 5 valid attachments during ticket creation.
- **FR-05 (My Tickets):** The system shall display a paginated list of tickets owned by the currently selected Requester.
- **FR-06 (List Controls):** The My Tickets list shall support searching by summary/number, filtering by category/priority/status, and sorting.
- **FR-07 (Ticket Detail):** A Requester shall be able to view the read-only details of their own ticket.
- **FR-08 (Attachment Download):** A Requester shall be able to download active attachments from their ticket.
- **FR-09 (Attachment Removal):** A Requester shall be able to soft-remove attachments from their ticket, making them no longer downloadable.
- **FR-10 (Access Control):** The system shall reject any attempt to view or manage a ticket or attachment that does not belong to the currently selected Requester.

## 5. Business Rules
- **BR-01:** The official Ticket Number is generated by the backend upon creation and must be unique (e.g., TKT-YYYY-XXXXXX).
- **BR-02:** A new Ticket begins with Current Status 'New'.
- **BR-03:** Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not secure authentication.
- **BR-04:** Ticket Summary is required and must be between 10 and 150 characters.
- **BR-05:** Ticket Description is required and must be between 20 and 1000 characters.
- **BR-06:** Attachments must be of type JPG/JPEG, PNG, WEBP, or PDF, and must not exceed 5 MB per file.
- **BR-07:** A maximum of 5 active attachments are allowed per Ticket.
- **BR-08:** Attachment removal must be implemented as soft removal; metadata is kept, but the file is removed from storage or marked unavailable for download.
- **BR-09:** Removed files must not be downloadable or previewed.
- **BR-10:** Only active Development Requesters can be selected.
- **BR-11:** If the backend attachment upload fails during ticket creation, the system must either rollback the ticket or explicitly warn the user. (Strategy: fail entire transaction if attachment upload fails).

## 6. UI Specification Summary
The UI will implement the **Zen Green Theme** as defined in `ui-spec.md`. Key elements:
- **Application Shell:** Top navigation bar with TokTickIT branding, selected requester profile, and primary navigation links (Create Ticket, My Tickets).
- **Create Ticket:** Form layout with visual distinction for read-only fields vs editable fields, using standard Zen Green component styles. Red asterisks for required fields.
- **My Tickets:** Responsive table or card list depending on viewport. Includes a search bar, filter dropdowns, and pagination controls.
- **Ticket Detail:** Read-only presentation of ticket data, separated attachment section with visual indicators for active vs soft-removed files.
- **Responsive Behavior:** Multi-column on desktop, single-column stacked on mobile.

## 7. Data Changes
The PostgreSQL database (managed via Prisma) will have the following models:
- **RequesterUser:** id (PK), name, email, isActive (Boolean).
- **Category:** id (PK), name (e.g., Account and Access, Hardware, Software, Network).
- **RelatedSystem:** id (PK), name (e.g., Email, Campus Wi-Fi, VPN, Corporate Laptop).
- **Ticket:** id (PK), ticketNumber (Unique), requesterId (FK), categoryId (FK), relatedSystemId (FK), requestedPriority, itPriority, currentStatus, summary, description, createdAt, updatedAt.
- **Attachment:** id (PK), ticketId (FK), fileName, originalName, fileType, fileSize, isRemoved (Boolean), removedAt, createdAt.

**Indexes:** `ticketNumber` (unique), `requesterId` (for list queries).
**Seed Data:** 4 active requesters, 1 inactive requester, 4 Categories, 6 Related Systems.

## 8. API Contract
See `api-spec.md` for detailed endpoint definitions.
- `GET /api/requesters`: Retrieve active requesters.
- `GET /api/reference-data`: Retrieve Categories and Related Systems.
- `POST /api/tickets`: Create a new ticket (with multipart/form-data for attachments).
- `GET /api/tickets`: Retrieve paginated list of tickets for the requester.
- `GET /api/tickets/:id`: Retrieve specific ticket details.
- `POST /api/tickets/:id/attachments`: Upload an attachment to an existing ticket.
- `DELETE /api/attachments/:id`: Soft-remove an attachment.
- `GET /api/attachments/:id/download`: Download an attachment.

## 9. Acceptance Criteria
- **AC-01:** Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed.
- **AC-02:** Given no Development Requester is selected, when the user attempts to open My Tickets or Create Ticket, then the Requester Selection screen is shown.
- **AC-03:** Given Requester B is selected, when a Ticket belonging to Requester A is requested via API, then the Ticket data is not returned (403 Forbidden or 404 Not Found).
- **AC-04:** Given a file larger than 5MB, when the user attaches it, then a validation error is shown and the file is rejected.
- **AC-05:** Given valid list parameters, when My Tickets loads, then it displays up to the page size limit of tickets owned by the selected Requester, sorted by newest first.
- **AC-06:** Given a ticket with an active attachment, when the user clicks remove, then the attachment is soft-removed and can no longer be downloaded.
- **AC-07:** Given a search term, when the user searches My Tickets, then only tickets matching the summary or ticket number are returned.

## 11. Assumptions and Decisions
- **Decision:** Soft-removed attachments will be kept on the filesystem/S3 for compliance, but the database flag `isRemoved` will prevent any API from serving the file to the frontend.
- **Assumption:** Ticket Number format `TKT-YYYY-XXXXXX` where `XXXXXX` is a zero-padded sequential ID or random hex. We will use zero-padded auto-increment or similar deterministic generation.
- **Decision:** Uploading attachments during ticket creation will be handled in a single transaction (multipart/form-data) to ensure consistency, rather than creating the ticket first and uploading files subsequently in the Create flow.
